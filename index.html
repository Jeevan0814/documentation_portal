Zero Trust–Enabled SDN Architecture for Secure and Intelligent Load Balancing in Edge Networks

Load balancers decide where to send work based on what servers say about themselves. Our SDN controller decides from what it observes instead. It scores every edge server on measured behaviour, and when a server misbehaves it revokes that server in the data plane as real OpenFlow rules, while a hash-chained ledger records why.

What's new since Panel Review 1

Every result below is from repeated live runs on the emulated network, usually five per arm. The sweep, the liar, witness, attestation and replica experiments were each scored against a prediction the team committed before running them.

  • The score can catch these attackers, but only just

    A threshold sweep showed the trust score alone isolates both task-completing attackers at θ = 0.45, 3.4× to 20× more slowly than the gate. At θ = 0.50 it also quarantined an honest server in one run.

  • A liar whose lie works

    80 further runs. A liar that lies only in the instantaneous load figure the router ranks on, while keeping its busy-time counter truthful, won +4.0 [3.47, 4.52] points of traffic above its fair share and was never quarantined. Ranking on the verified figure removed the gain (+0.01 points) at no measured honest cost, and is now the default.

  • A defect in our own honesty check, found and fixed

    At 40% server occupancy the honesty check falsely quarantined 3.0–4.4 honest servers per run, because it measured a server's rate only up to its last completion. After two fixes, 0.2 per run. The defect is latent at the normal workload: no ablation or sweep run saw it fire on an honest server.

  • The switches as a third witness

    Joining each connection's switch counters with the client's report named the lying party (a dropping server, a hiding switch, a badmouthing client, or a dropper covered by a colluding switch) in 25 of 25 runs, with no honest party blamed.

  • Attestation beside behaviour

    A server with a tampered image was refused at admission in 5 of 5 runs and handed no work; unattested, it took 6–25 connections before the gate caught it. A server compromised at run time passed every quote, and only behaviour caught it.

  • Replicas that check the controller

    Ledger replicas that replay the trust arithmetic rejected every forged score that reached them, 5,478 records with none rejected falsely. A controller that forges the evidence instead passed them; only the switch witness exposed it.

  • Raft in the live controller

    The ledger can now commit to a 3-replica Raft cluster. With the leader killed mid-run, a new leader took over in 0.47 s and all 649 of 649 updates were committed. Commits took 14 ms on average, 20 ms at p95.

  • Flood throttling in the switch

    A per-client meter now throttles a flooding device. Under a heavy flood, honest devices' p95 latency fell from 177.7 to 139.4 ms and the tasks served to the flooder fell 97%, with no honest device ever throttled.

Where this sits. Misreporting attacks on load balancers are known on the switch side: a compromised switch falsifies its traffic statistics to draw load (Burke et al. 2023), can do so while evading threshold detectors (Yu et al. 2024), and can be flagged by a learned detector (Saha et al. 2025); SPHINX (2015) checks flow statistics for consistency along a path. This work studies the server-side counterpart: a server misreporting its own load. We also retracted a claim from earlier work: containment did not cost attack attribution (ρ = −0.52, p = 0.12, n = 10).

Problem statement

Can an SDN control plane continuously verify edge servers using observed rather than claimed behaviour, and enforce the verdict in the data plane fast enough to matter?

The perimeter fails at the edge

Edge servers sit in roadside cabinets, factory floors and campus racks. Any of them can be opened, rented out, misconfigured or simply selfish. Round-robin and least-connections assume every backend is honest and does its work; neither can ever notice when one isn't.

Self-reported telemetry is easy to game

Kubernetes, cloud auto-scalers and MEC orchestrators all schedule on what nodes claim about themselves. A node that under-reports its load attracts traffic. The attacker breaks no cryptography; it only lies in a field everybody believes.

Zero Trust is a policy, not a mechanism

NIST SP 800-207 says never trust, always verify, continuously. Most products verify users and devices at login. Verifying the serving infrastructure itself, continuously, with routing consequences, is far less settled. That gap is where this project works.

Scope. We demonstrate one mechanism, behavioural trust plus SDN enforcement, under six modelled attacks, in an emulated network (Mininet with real Open vSwitch and OpenFlow 1.3). We don't claim to solve Zero Trust for edge networks in general, and we don't claim production deployment.

Project objectives

  • Score servers on behaviour, continuously

    Compute a trust score for every edge server from task outcomes, response time, honesty about load and anomaly signals, updated after every interaction.

  • Route by trust and load together

    Send each new connection to a server that is both trusted and not overloaded, using an EdgeScore with power-of-two-choices sampling.

  • Enforce verdicts in the data plane

    Quarantine a misbehaving server as real OpenFlow rules and re-steer its in-flight work, within a 3-second bound.

  • Admit only real devices

    Authenticate IoT devices with a PRESENT-80 challenge–response, pinned to each device's provisioned source IP.

  • Keep a tamper-evident record

    Commit every trust update to a SHA-256 hash-chained ledger with a Merkle root per block, replicated by Raft.

  • Prove it against a control arm

    Run the same network, workload and attacks with and without zero trust, and back the difference with statistics over 600 seeded runs.

Methodology

The product is an os-ken (Ryu fork) OpenFlow 1.3 controller application with a REST and server-sent-events API and a live dashboard. Mininet, the edge-server agents and the IoT clients are its test harness.

How one task flows

  1. A

    Admission, once per device

    The device requests a 64-bit nonce, encrypts it under PRESENT-80 and sends it back. The controller checks the response and the source IP against the provisioned roster. Failure returns 403 and logs the reason.

  2. B

    Routing, once per connection

    The device connects to a virtual IP. The switch asks the controller, which filters to eligible servers, samples two, scores them by EdgeScore and installs rewrite rules to the winner.

  3. C

    Execution and verdict, once per task

    The server does real work, the client reports the outcome and latency, and trust is updated. Every second the controller also polls each server's status and compares claims with observations.

  4. D

    Enforcement, when a server fails verification

    Trust below 0.30, or the anomaly gate firing, triggers one cookie-matched rule delete, drop rules, and re-steering of in-flight work. A probation path lets a recovered server earn its way back.

The trust model

T = α·R̄ + β·B̄ + γ·H̄ − δ·Ā

α = 0.35, β = 0.25, γ = 0.25, δ = 0.15, with exponential decay λ = 0.85

Terms of the trust formula
TermMeasured from
R̄ ReliabilityCompleted versus failed tasks
B̄ BehaviourResponse time against the fleet median
H̄ HonestyClaimed load versus the duty cycle the controller derives
Ā AnomalyLatency, timeout-rate, honesty and flood tells

Isolation threshold 0.30. Anomaly gate 0.50. Routing uses EdgeScore w₁·T + w₂·(1 − cpu) + w₃·(1 − latency), where cpu is the busy-time duty the honesty check verifies, with weights tuned online by a UCB1 bandit.

What the gate buys, and what it costs. Both acting arms deliver almost the same service; what the gate adds is containment and the latency tail: p95 falls from 175.6 to 137.2 ms and the share of routes reaching attackers from 17.37 to 11.63 %. Against the baseline, mean latency is 4.2 ms worse with both rails, and the throughput intervals overlap. No honest server was falsely quarantined at this workload; at 40 % occupancy a since-fixed defect in the honesty check did quarantine honest servers (see What's new).

Detection quality

With both rails, all eight attacks were placed in the right family in all five runs. The exact label was right for 7 of 8 in four runs and 6 of 8 in one. The recurring miss is the blackhole labelled grayhole: once it is quarantined at about 10 s it receives almost no traffic, so the timeout-rate tell never accumulates a measured rate. None of the 40 honest subjects was placed in an attack class, in any arm or run.

Statistical evidence over 600 seeded simulations

Live runs give fidelity; a seeded simulation gives repetition. It drives the real selector, trust calculator and detectors: 5 strategies × 4 scenarios × 30 seeds. Paired Wilcoxon signed-rank tests with Holm–Bonferroni correction show 14 of 16 comparisons significantly favour the system (padj = 7.45 × 10⁻⁹, the smallest value the test can return at n = 30). The two losses are in the attack-free scenario: 10.7 % worse than round-robin and 4.8 % worse than random.

Research paper

Draft manuscript, revision 7, 23 October 2026. Not yet submitted.

What Catches a Lie That Works? Trust Scores, Anomaly Gates and Load-Misreporting Servers in Zero-Trust Edge Load Balancing

K R Jeevan Raj, Aravind Kumar M, Arjun Krishnakumar, Ashwin Kumar RM, Bhuvanesh S. Faculty guide: Dr. Radhika N.

Abstract

Zero Trust demands continuous verification but does not say how a network control plane should verify the servers it routes work to. We built a Zero-Trust SDN load balancer in which a trust score ranks edge servers, an independent anomaly gate excludes them, and every verdict is installed as OpenFlow 1.3 rules, and evaluated it live on an emulated 8-server, 40-device edge. In a five-run-per-arm ablation the score never isolated two attackers that complete every task while the gate isolated both every time; a threshold sweep shows the score can, but only within a band a few hundredths wide and 3.4–20× more slowly. Those attackers were slow: the gate had caught a slow server, not a lie.

In 80 further runs, each against a prediction registered first, a liar serving at honest speed with internally consistent claims gains nothing, while one that lies only in the instantaneous load figure the router ranks on, with a truthful busy-time counter, wins 4.0 points of traffic above its fair share and is never caught; ranking on the verified figure closes the hole at no measured honest cost. Emulated mixed hardware is not mistaken for lying; switch counters joined with client reports name the lying party in 25 of 25 runs; attestation stops a tampered server before it serves; and ledger replicas that replay the trust arithmetic reject every forged score, yet a controller forging evidence passes them, blinds its own detectors, and only the switches expose it.
